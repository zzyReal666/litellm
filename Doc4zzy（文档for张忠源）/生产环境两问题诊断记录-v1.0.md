# 生产环境两个问题诊断记录

版本 v1.0
日期 2026-11-25
环境 192.168.7.99 中安云科 AI 安全网关，镜像 litellm-zhcn:v1.106.0-zh.15
说明 本文只记录诊断结论与复现方案，生产环境未做任何配置或代码改动

## 问题一：用量页 Ask AI 提示所选模型无法直接调用

### 现象

用量页面点「询问 AI」，选中一个在模型测试连接、训练场都能正常使用的模型分组，发送问题后返回

```
错误：所选模型无法直接调用，请选择一个已配置凭据的模型分组。
```

### 现场验证

用管理员密钥直接调用后端接口，使用模型组名

```
POST /usage/ai/chat
{"messages":[{"role":"user","content":"本月总花费是多少？"}],"model":"deepseek-v4-flash"}

返回 SSE：
data: {"type": "status", "message": "Thinking..."}
data: {"type": "error", "message": "An internal error occurred. Please try again."}
```

不传 model 参数同样失败。模型分组在 `/v1/chat/completions` 与 `/v1/models` 下均正常，说明模型本身可用，失败发生在 Ask AI 自身的调用链。

### 根因

部署版本 `litellm-zhcn:v1.106.0-zh.15` 中的 `ai_usage_chat.py` 直接用 SDK 调用

```
response = await litellm.acompletion(model=resolved_model, messages=chat_messages, tools=tools, ...)
```

Ask AI 从界面拿到的是模型分组名（例如 `deepseek-v4-flash`），而 `litellm.acompletion` 只认带提供方前缀的模型名，无法解析代理侧的分组，于是报错。训练场和测试连接走的是代理路由，能解析分组，所以同样一个模型在两处表现不一致。

同时部署版本的异常处理把所有错误统一映射成 "An internal error occurred"，前端拿不到可区分的错误码，因此界面上出现的提示与真实原因不一致。

### 仓库中的修复

分支 `zayk-dev` 已包含修复提交

```
8efd75179e fix(usage): route Ask AI model calls through the proxy router
```

改动内容

1. `ai_usage_chat.py` 新增 `_usage_ai_completion`，优先通过 `router.acompletion` 调用，让代理路由把模型分组解析成带凭据的部署；无 router 时（单元测试）回退 SDK。
2. 新增 `_classify_usage_ai_error`，按真实原因返回 `provider_credentials_missing`、`model_not_available`、`rate_limited`、`internal_error`，前端根据错误码给出对应提示。
3. `_resolve_usage_ai_model` 在未选择模型时默认取第一个可用分组。
4. `endpoints.py` 调用时传入 `router=llm_router`。
5. 前端补充错误码映射与文案。

与新版本比对，部署版本的两处文件差异为：`endpoints.py` 缺 2 行（router 导入与传参），`ai_usage_chat.py` 差异 141 行。

### 测试环境修复方案

取 `zayk-dev` 上 `8efd75179e` 及之后的版本构建镜像，或最小化替换以下两个文件

```
litellm/proxy/management_endpoints/usage_endpoints/ai_usage_chat.py
litellm/proxy/management_endpoints/usage_endpoints/endpoints.py
```

两个文件在此提交之后均无后续改动，可直接替换。

### 验证步骤

1. 用管理员密钥调用 `POST /usage/ai/chat`，body 指定 `"model":"deepseek-v4-flash"`，期望返回 `status` 后跟 `chunk`/`done`，不再出现 `error`。
2. 不传 `model`，期望默认取第一个分组并正常返回。
3. 页面操作：用量页面打开「询问 AI」，选择模型后提问，期望正常输出分析结果。
4. 异常分支：指向一个无凭据的分组，期望提示凭据缺失而不是无法直接调用。

## 问题二：DeepSeek 返回 stream_options 参数错误

### 现象

请求 ID `7323587f-e4ec-40be-ad49-0bc3ea6980e2`，2026-11-25 09:34（+08），返回

```
400 litellm.BadRequestError: DeepseekException
{"error":{"message":"stream_options should be set along with stream = true","type":"invalid_request_error"}}
LiteLLM: model group 'deepseek-v4-flash' failed with the error above. No fallback was attempted.
```

### 现场数据

从用量库取该请求的完整入站请求体

```
request_id   7323587f-e4ec-40be-ad49-0bc3ea6980e2
时间          2026-11-25 01:34:02 UTC
调用类型       acompletion
部署            d8e69226（官方 deepseek）
token 数       233,686
客户端         ZCode/3.16.3（ai-sdk/provider-utils）
stream         true
stream_options {"include_usage": true}
thinking       {"type": "enabled"}
reasoning_effort max
max_completion_tokens 384000
tools          44 个
messages       526 条
```

关键点：入站请求携带 `stream: true` 和 `stream_options`，而 DeepSeek 报错说明它收到的请求体里只有 `stream_options`、没有 `stream=true`。

同类失败近 7 天共 10 次，全部集中在 ZCode 客户端（`ai-sdk` 系客户端默认携带 stream_options），随机分布在四个官方部署上，全部是超长上下文请求。

### 代码路径分析

上游参数组装在 `litellm/llms/custom_httpx/llm_http_handler.py` 的 `_add_stream_param_to_request_body`

```
if fake_stream is True:
    new_data = data.copy()
    new_data.pop("stream", None)      # 移除 stream
    return new_data
if provider_config.supports_stream_param_in_request_body is True:
    data["stream"] = True             # 流式时补上 stream
return data
```

也就是说，只要本次调用被判定成非流式或者 fake_stream，请求体里就不会有 `stream`，但客户端带来的 `stream_options` 仍然留在 `data` 里原样发出，DeepSeek 严格校验后返回 400。

这是 LiteLLM 的已知问题类型，上游仓库有同源 issue

- https://github.com/BerriAI/litellm/issues/29431 非流式请求携带 stream_options 导致后端 400

该 issue 已关闭，但本环境版本仍可复现，说明当前镜像中的某条路径仍会把 stream_options 带到非流式请求里。

### 待测试环境确认的点

生产环境不能加日志，以下两点需要在测试环境用 debug 日志确认

1. 本次上游调用为何是「非流式」。怀疑方向有两条：一是 `fake_stream` 被置为 True，二进制日志里能看到 `stream` 被 pop 掉；二是 LiteLLM 内部重试链路复用了携带 stream_options 的参数走非流式分支。测试环境打开 `LITELLM_LOG=DEBUG`，日志会输出 `POST Request Sent from LiteLLM` 的完整 curl 与请求体，可直接看到 stream 是否存在。
2. 507 条消息、44 个工具的超长请求是否触发了特殊路径（例如 keepalive 包装 `open_sse_before_first_byte`，该请求的调用栈确实经过这个包装）。

### 建议修复方式

防御式处理，在发往 provider 之前按 stream 状态决定 stream_options 去留，避免依赖调用路径。

可选位置

1. `_add_stream_param_to_request_body`：fake_stream 分支同时移除 `stream_options`。
2. 非流式 dispatch 分支（`async_completion` 调用前）：若 `stream` 不为 True，从 data 中移除 `stream_options`。
3. 代理层 `_stream_usage_tracking_updates` 已有 `if data.get("stream") is not True: return` 的判断，可在更下游再加一道一致的保护。

推荐做法是第 2 条，覆盖所有非流式调用路径，改动小且不影响流式请求。

### 测试环境复现步骤

1. 准备与现场一致的请求：`stream: true`、`stream_options: {"include_usage": true}`、`thinking: {"type":"enabled"}`、`reasoning_effort: "max"`、`max_completion_tokens: 384000`、40 个以上 tools、500 条以上 messages，模型为官方 deepseek 分组。
2. 打开 debug 日志，重复发起请求，观察 `POST Request Sent from LiteLLM` 的请求体是否出现只带 stream_options 不带 stream 的情况。
3. 命中后按上述建议修复，回归验证：同一请求恢复 200 且流式正常，同时确认普通流式请求的 usage 统计未受影响。

## 附：本次诊断使用的查询

用量库表 `LiteLLM_SpendLogs`，其中 `proxy_server_request` 字段保存完整入站请求体，`metadata` 字段保存错误信息与路由元数据。

```
-- 按请求 ID 定位
SELECT * FROM "LiteLLM_SpendLogs" WHERE request_id = '<请求ID>';

-- stream_options 相关失败统计
SELECT "startTime", model_id, call_type,
       metadata->'error_information'->>'error_message'
FROM "LiteLLM_SpendLogs"
WHERE "startTime" > now() - interval '7 days'
  AND status = 'failure'
  AND metadata->'error_information'->>'error_message' LIKE '%stream_options%'
ORDER BY "startTime" DESC;
```
