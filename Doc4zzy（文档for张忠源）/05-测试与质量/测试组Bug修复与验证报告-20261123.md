## 十、询问 AI 与表单提示修复（11-24，zh.31）

### 询问 AI 误报「所选模型无法直接调用」

现象：用量页询问 AI 选择模型后提示「所选模型无法直接调用」，但该模型在模型测试连接和试验场都能正常使用。

根因：询问 AI 后端把模型分组名（如 `deepseek-v4-flash`）直接传给 `litellm.acompletion`，SDK 无法解析代理上的模型分组，报 `LLM Provider NOT provided`；错误分类又把所有 `BadRequestError` 都当成「模型不可调用」，于是给出误导性提示。

修复：提供模型调用统一入口，优先通过代理 Router 的 `acompletion` 解析模型分组与部署，只在没有 Router（单元测试）时回退 SDK；未选择模型时默认取第一个已配置模型分组；错误分类改为按真实原因区分凭据缺失、限流、模型不可用和内部错误。前端补充「模型不可用」的中文提示，模型占位文案同步为「默认使用第一个可用模型」。

## 二十一、压缩护栏地址与压缩效果排查（11-27）

反馈：112 上压缩护栏配置的地址是 `http://headroom:8787`，看起来像外网地址，担心压缩不生效。

地址说明：`headroom` 是 docker compose 的服务名，不是公网域名。litellm 容器与 headroom 容器同在 composing 网络 `litellm_default` 上，容器内通过 Docker 内嵌 DNS 把 `headroom` 解析到容器 IP（实测 172.18.0.2），请求 `http://headroom:8787/livez` 返回 200；宿主机只把 headroom 发布在 `127.0.0.1:8787`，外部无法访问。因此该地址是标准的容器间内网地址，流量不出主机，配置正确，不需要改成公网地址。

实测发现两个独立问题：

1. 手动创建的护栏缺少鉴权。headroom 的 `/v1/compress` 需要 `HEADROOM_PROXY_TOKEN`，用户手动建的「测试压缩配置」没有 api_key，headroom 日志 `proxy_auth_rejected ... reason=missing_token`，litellm 侧报 502 `Headroom compression service returned an error (401)`，且默认 fail_closed 会阻断请求。已通过 API 修正该护栏：补 api_key 并设置 `unreachable_fallback=fail_open`。安装脚本 `scripts/setup-compression.sh` 创建时本来会带上这两项，界面手工创建容易漏。

2. headroom 镜像内压缩模型不完整，压缩实际不生效。日志显示 `Kompress model not ready; requests will not be compressed`，ONNX 加载失败后回退 PyTorch，提示无法连接 huggingface.co 且缓存中缺文件。检查镜像缓存：`/root/.cache/huggingface/hub/models--chopratejas--kompress-v2-base` 只有 ONNX 权重 blob，缺 config、tokenizer 等仓库文件；而目标机无法访问 huggingface.co。结果是 headroom 每次请求都原样透传，日志 `compressed=0`、`tok_before=3083 tok_after=3083 tok_saved=0`。

结论：地址配置正确，压缩服务网络通、鉴权已修复；但压缩省 token 要等 headroom 镜像补齐完整模型缓存。需要重新构建 headroom 镜像（zh.8），在构建时把 kompose-v2-base 完整仓库（config/tokenizer + ONNX）预置到 `/root/.cache/huggingface`，并更新 compose 与安装包中的 headroom 镜像 tag；完成后复测 headroom 日志出现 `Headroom: compressed X -> Y` 与 `tokens_saved > 0` 即算通过。

## 二十二、压缩护栏鉴权与中文护栏名响应头问题（11-27）

问题一：在「成本优化 → 提示词压缩」里创建的压缩护栏不填写 api_key，依赖环境变量鉴权，当前配置能否通过？

结论：现在能通过，但安装包原样部署时不能。护栏 hook 在没配置 api_key 时的回退变量是 `HEADROOM_API_KEY`（`get_secret_str("HEADROOM_API_KEY")`），而安装包此前只给 headroom 服务和 litellm 容器注入了 `HEADROOM_PROXY_TOKEN`，网关容器里没有 `HEADROOM_API_KEY`，所以成本优化创建的免 Key 护栏会不带 Authorization 调用 headroom，被 401 拒绝，fail_closed 下还会阻断业务请求。

修复：在 `deploy/offline-package/docker-compose.yml` 的 litellm 服务环境变量中增加 `HEADROOM_API_KEY: ${HEADROOM_PROXY_TOKEN}`。实机更新 112 的 compose 并重建 litellm 容器后，把护栏改成不带 api_key（模拟成本优化创建方式），请求 headroom `/v1/compress` 返回 200，无 proxy_auth_rejected，鉴权通过。

问题二：验证过程中发现中文护栏名会导致业务请求全部 503。响应头 `x-litellm-applied-guardrails` 直接拼接护栏名，名称为中文时 Starlette 按 latin-1 编码响应头失败，抛 `UnicodeEncodeError: 'latin-1' codec can't encode characters`，表现为每次请求 503 且日志误报数据库不可用。

修复：`get_logging_caching_headers` 统一对响应头值做 latin-1 安全处理，非 ASCII 字符按 UTF-8 百分号编码，ASCII 名称保持原样。新增单测覆盖中文护栏名与策略名的响应头可编码且编码结果正确，以及 ASCII 名称不变。实机替换容器内该文件并重启后，用中文名护栏触发请求不再出现 503 与 UnicodeEncodeError，响应头返回 `x-litellm-applied-guardrails: %E6%B5%8B...`。

待办：上述 compose 与后端代码改动需要重新构建镜像（zh.40）并重打安装包才会固化到交付物；当前 112 的 litellm 容器是手动替换文件后的状态，重建容器会回退。压缩模型缓存不完整导致空转的问题仍在，另行处理。
