# 禅道 Bug 处理标准流程与 Skill 使用说明

版本 v1.0
日期 2026-11-24
适用 中安云科 AI 安全网关（LiteLLM 中文版）测试组 Bug 处理与交付
配套 Skill `zentao-bug-fix`（仓库路径 `.dsh/skills/zentao-bug-fix/`）

## 一、目的

测试组在禅道提交的 Bug 往往只有标题，重现步骤和期望为空，而且涉及中文化、参数校验、错误提示、交互刷新、安装包版本等多个层面。只按标题字面改代码，容易漏、容易改错，也说不清楚「改完了没有」。

本文把上一轮实际跑通的流程固定下来，目标是每轮 Bug 处理都能做到：清单完整、根因清楚、修复可回归、验证有证据、交付可追溯，并且同一套动作可以由任何人重复执行。

## 四、标准流程

整体分八个阶段，每个阶段都有明确产物，阶段之间不跳步。

### 阶段 1：拉取与梳理

动作：

- 抓取禅道列表与详情，得到本批 ID 集合；
- 与上一轮「已处理 ID 集合」对比，识别新增/重新激活项；
- 按模块分组，记录标题和状态。

产物：本轮 Bug 清单文档（含每条的表现推断、期望、处理结论）。

要点：禅道详情经常为空，不要等详情；标题 + 实机操作是主要信息来源。清单文档追加到上一轮文件或新建按日期的文件，并在文末维护「已处理 ID 集合」，方便下一轮 diff。

### 阶段 2：复现与定性

动作：

- 先用 recon 脚本把相关页面的按钮、输入、下拉、文本 dump 出来，确定操作路径；
- 再写精准复现脚本，记录当前现象、触发路径、根因；
- 判定是否为新回归：与修改前基线对比失败用例集合；
- 给问题归类：翻译缺失/硬编码、授权或 premium 门控、结构化错误被吞、静默 return、显示值与选项不一致、校验缺失、错误码未分类等。

产物：每条 Bug 的复现记录（`/tmp/repro_*.json` 或截图）。

要点：标题相同的问题根因可能完全不同。例如「提示信息需要优化」可能是前端拼英文前缀、后端返回结构化对象、或错误被统一吞成 internal error。必须先定性再动手。

### 阶段 3：修复

动作：按根因修复，并同步补回归测试。

必须遵守的项目约定：

- 中文产品默认全中文：新增文案走 `i18n.t(key, { defaultValue })`，同时补 `src/locales/zh-CN.json` 和 `en.json`，两边 key 必须一致；`src/lib/i18n.test.ts` 会校验。
- 错误提示面向用户：不直接透出异常文本；前端能校验的在提交前校验并显示行内错误；后端结构化错误在前端映射成中文可操作提示，必要时后端增加错误码。
- 非法输入不能静默失败：把静默 `return` 改成设置表单错误并阻止提交。
- 每个修复必须有回归测试：修复前失败、修复后通过，断言行为而不是结构，不把第三方事实写死。
- 前端改动跑 `tsc`；后端改动跑对应 `pytest`。
- 提交信息用 conventional commits。

产物：代码改动 + 新增/更新测试。

### 阶段 4：测试

动作：

1. 跑受影响目录的 vitest 子集；
2. 与修改前基线对比失败文件集合，确认新增失败为 0；
3. 后端改动跑对应单元测试；
4. 需要时再跑一次相关全量。

产物：测试结论（通过数、与基线对比结果、遗留失败说明）。

要点：仓库前端有大量历史失败用例，不对比基线就无法证明「没有回归」。基线用 `git worktree` 建，软链 `node_modules`，按失败文件 diff。

### 阶段 5：构建与部署

动作：

1. 前端 `npm run build` 生成 `out/`；
2. 后端只覆盖改动的 `.py` 文件；
3. 在 112 用叠层 Dockerfile 构建新镜像并 `force-recreate`；
4. 健康检查。

产物：部署到测试机的新镜像，容器 healthy，`/ui/` 返回 200。

要点：compose 的 `environment` 优先级高于 `.env`；授权门禁等开关要在 compose 改并记录，测完恢复。镜像构建时间早于最后一次提交时必须重建。

### 阶段 6：实机验证

动作：写 `verify_*.mjs`，登录后逐条走操作路径，断言关键文本/状态，输出 JSON 证据；无法完整验证的（依赖有效授权、依赖真实上游）标注「部分验证」并写明原因。

产物：验证 JSON/截图，以及每条 Bug 的验证结论。

要点：证据要能复述操作路径和结果，不能只写「已修复」。

### 阶段 7：出包与文档

动作：

1. 版本号升级（安装脚本、compose、README、安装教程同步）；
2. 测试机上复制上一版解压目录，替换镜像 tar，`tar` 打包并生成 sha256，放到 `/opt` 并解压核对；
3. 更新验证报告（结论、测试、包 sha256、镜像 ID、测试实例状态）；
4. 安装教程改完重新生成 docx/pdf；
5. 本机 Downloads 同步安装包并核对 sha。

产物：新版本安装包（tar.gz + sha256）、更新后的报告与文档。

要点：交付件版本号只升不降；报告里的 sha256 必须和实际包一致。

### 阶段 8：提交与推送

动作：按主题拆分提交（代码修复、QA 工具、文档、发布），`git add` 指定路径，推 `origin` 和 `gateway` 两个远端，确认 SHA 一致。

产物：远端最新提交，工作区干净。

要点：不要 `git add -A`，避免把其他会话的 WIP（如 `deploy/arm64/`）带进去；推完检查两个远端 SHA。

## 五、质量红线

- 文案：中文产品不新增英文；i18n key 双语成对；品牌名、单位、模型 ID 等确实不翻译的除外。
- 错误提示：不出现技术堆栈、英文异常、`[object Object]`、只显示「操作失败」。
- 校验：非法 JSON、超长文本、负数限额、重名等必须在前端给出明确提示。
- 测试：每个修复有能挡住回归的测试；无新增失败。
- 证据：每条 Bug 有可复述的验证路径和结果；报告有包 sha256。
- 安全：账号、密码、授权文件、token 不进仓库和文档。

## 七、常见问题

1. 禅道详情为空怎么办？按标题和实机操作推断「表现/期望」，在清单里写推断依据。
2. 怎么判断中文页面里的英文是不是 Bug？品牌词、协议名、单位（Token/UTC/TTL）、模型 ID、日期格式（en-US 由共享格式化器产生）不算；按钮、标签、提示、占位符、空状态、toast 是。
3. 为什么修完按钮还是没反应？先看是否被表单校验挡住、是否静默 return、是否 premium/授权门控、是否缓存未失效。
4. 为什么测试「全绿」但测试组复测又提？因为只跑了用例没实机验证，或者镜像不是包含修复的构建。必须实机 + 版本核对。
5. 授权过期导致企业版功能无法回归怎么办？在报告中标注「部分验证」并写明依赖，不要假设通过。
6. 登录接口用 curl 调试返回 401 怎么排查？登录接口只接受 form 编码，JSON body 会被当成空用户名密码。
