# AI 效能统计与 ROI 度量方案

| 项目 | 内容 |
|---|---|
| 版本 | v0.1 草案 |
| 日期 | 2026-10-26 |
| 状态 | 待评审，未进入开发 |
| 适用范围 | AI Token 网关、研发编码辅助场景 |
| 数据基础 | litellm 网关日志，可选接入 Git 平台数据 |

## 1. 背景与目标

网关目前能精确计量 token、成本和调用情况，但管理层还需要回答「AI 用得是否高效、投入是否值得」。本方案把度量拆成两层：一层是成本与过程指标，用现有日志就能算准；另一层是产出与价值指标，需要接入 Git 平台并配套基线和参数折算。

目标有四个：成本可审计、效能可对比、价值可估算、结论可追溯。明确不做三件事：内容对错的全量判定、开发者个人排行榜、把 token 量当效率。

## 2. 设计原则

| 原则 | 说明 |
|---|---|
| 以 session 为核心粒度 | 编码辅助的工作单元是一次连续 session，request 只是其中一步 |
| 区分 fresh token 与 cache token | total_tokens 里 cache read 占大头，直接当使用强度会高估 |
| 可靠性不叫质量 | 网关日志只能证明调用稳不稳，证明不了答案对不对 |
| 记分卡不做单一总分排名 | 综合分用于排序和趋势，必须可下钻到原始指标和样本量 |
| 个人与团队分层 | 个人层做用量和配额，团队层做评分和 ROI，两层互不引用 |
| 口径与权重版本化 | 口径或权重一变，历史分数要能重算或冻结 |

### 3.3 两套方案的能力边界

| 要回答的问题 | 仅 litellm | litellm + Git |
|---|---|---|
| AI 花了多少钱 | 可精确 | 可精确 |
| 每单位 AI 使用花多少钱 | 可精确 | 可精确 |
| 每单位产出花多少钱 | 不可 | 可算 |
| 研发产出有没有提升 | 不可 | 可实测 |
| 提效多少、折成多少钱 | 不可 | 可估算，需参数和对照 |
| 内容质量对不对 | 不可 | 不可，需反馈或评审 |
| 业务收入与价值 | 不可 | 不可，需业务系统数据 |
| ROI | 只能算成本侧 | 可算收益侧，给区间 |

## 4. 个人层与团队层分开

### 4.1 两层定位

| 项目 | 个人层 | 团队层 |
|---|---|---|
| 定位 | 运营工具 | 管理工具 |
| 目的 | 配额、成本归属、异常识别、自查 | 效能评估、ROI、预算分配、复盘 |
| 评分 | 不出分 | 五维记分卡加 ROI |
| 排名 | 禁止 | 团队之间可对比 |
| 可见范围 | 本人加管理员 | 团队负责人加管理层 |
| 主要用途 | 限额、授权、支持 | 对外汇报、预算决策 |

### 4.2 个人层指标

| 分组 | 指标 | 口径 | 数据来源 |
|---|---|---|---|
| 用量 | 活跃天数 | 有请求的自然日 | 现有 |
| 用量 | 请求数 | 按 user_id 汇总 | 现有 |
| 用量 | session 数 | 按 session_id 去重 | 新增 session 表 |
| 用量 | fresh token 与 output token | 扣除 cache read | 新增 session 表 |
| 成本 | 月成本 | 按 user_id 汇总 spend | 现有 |
| 成本 | 额度使用率 | 已用额度除以配额 | 新增计算 |
| 成本 | 剩余额度、超限预警 | 配额减已用 | 新增计算 |
| 可靠性 | 成功率 | 成功请求除以总请求 | 现有 |
| 可靠性 | 错误分布、重试次数 | 按错误类型汇总 | ErrorLogs |
| 可靠性 | 延迟 | p50、p95 | 现有 |
| 异常 | 用量突增突降 | 对个人基线做稳健 z 分数 | 新增计算 |
| 异常 | 高失败率、闲置后集中调用 | 规则匹配 | 新增计算 |

| 结论 | 五维记分卡、ROI 区间 | 聚合值加参数折算 | 新增 |

### 4.4 计算规则

| 规则 | 做法 | 原因 |
|---|---|---|
| 团队率值 | 用和之比 | 避免个人均值被小样本拉偏 |
| 团队分 | 由团队聚合值计算 | 个人没有分，不能加总 |
| 人员变动 | 用量按天归属 | 换团队时费用拆给对应团队 |
| 人均分母 | 团队人数用月快照 | 人数变化时历史人均指标可比 |
| 最小样本 | 低于阈值不出比率、不给分 | 防止日波动造成误判 |
| 两层加权 | 不相加、不互相引用 | 防止个人数据污染团队评分 |

### 4.5 权限矩阵

| 角色 | 个人层 | 团队层 |
|---|---|---|
| 普通用户 | 仅自己 | 所属团队汇总，或不可见 |
| 团队负责人 | 本团队成员用量 | 本团队全部指标与评分 |
| 管理员 | 全部 | 全部团队与产品线 |
| 财务 | 成本与额度 | 团队成本汇总，不看明细 |

### 4.6 记分卡归属

| 评分项 | 个人 | 团队 |
|---|---|---|
| 采纳 | 不评分 | 25% |
| 深度 | 不评分 | 15% |
| 可靠性 | 不评分 | 20% |
| 成本效率 | 不评分 | 25% |
| 价值 | 不评分 | 15% |
| 综合分 | 无 | 有 |
| ROI 区间 | 无 | 有 |

### 4.7 反模式

| 反模式 | 问题 | 替代做法 |
|---|---|---|
| 个人排行榜 | 改变使用行为，指标失真 | 只给管理员看用量 |
| 个人效率分 | 无法可靠归一化 | 个人层不评分 |
| 个人均值算团队分 | 小样本会拉偏结果 | 用和之比计算 |
| 跨人比较成本 | 任务难度差异大 | 只做团队间对比 |
| 个人指标加总当价值 | 用量不等于产出 | 价值只用团队加 Git 数据 |

## 5. 评分模型

### 5.1 五维记分卡

| 一级分 | 权重 | 子指标 | 归一化方式 |
|---|---|---|---|
| 采纳分 | 25% | 渗透率、人均 session 数、周增长 | 相对百分位 |
| 深度分 | 15% | session 深度、cache 占比、工具调用 | 相对百分位 |
| 可靠性分 | 20% | 成功率、错误可控度、截断空响应、延迟 | 绝对目标达成率 |
| 成本效率分 | 25% | 每 session 成本、cache 命中、高阶模型占比、每 PR 成本 | 绝对目标达成率 |
| 价值分 | 15% | 人均合并 PR、返工率、评审意见、PR 周期 | 相对百分位 |

价值分在 Git 数据接入前按比例回填到其他四项，并在页面标注「价值未接入」。

### 5.2 归一化方法

| 方法 | 公式 | 适用场景 |
|---|---|---|
| 相对分 | 同规模团队内百分位排名乘以 100 | 横向对比 |
| 绝对分 | clamp(实际值除以目标值, 0, 100) | 看进步 |

### 5.3 提升度

本期对基线期，基线可配置，默认接入前 30 天或上一季度同长度窗口。研发场景优先用交错接入的差分对比：先接入组与后接入组比较前后同周期的人均合并 PR、返工率、PR 周期，用人头归一化，8 周窗口。比简单前后对比更可信。

### 5.4 防作弊规则

| 规则 | 内容 |
|---|---|
| 量类指标 | 只进采纳维度，按活跃开发者归一化 |
| 成本效率 | 分母用成功请求 |
| 极端值 | winsorize 1%/99% |
| 最小样本 | 日请求低于 100 标样本不足，不给分 |
| 权重版本 | 写入分数表，改版后历史重算或冻结 |
| 个人排名 | 禁止 |

## 6. ROI 度量

### 6.1 五层框架

| 层级 | 数据性质 | 内容 | 置信度 |
|---|---|---|---|
| L0 成本台账 | 精确可审计 | token 成本、GPU 分摊、平台运维、接入培训 | 高 |
| L1 单位经济性 | 精确到实测 | 每 session 成本、每活跃人天成本、每合并 PR 成本 | 高 |
| L2 效率增量 | 实测需对照 | 合并 PR、PR 周期、返工率、评审意见的变化 | 中 |
| L3 价值折算 | 估算参数透明 | 实测增量按时薪、转化率、返工成本折成金额 | 中低 |
| L4 归因与不确定性 | 结论层 | 给保守、基准、乐观三档区间，附敏感性分析 | 取决于参数 |

### 6.2 公式

```text
总成本 C = token 成本 + 本地算力分摊 + 平台运维人力 + 接入培训 + 其他
总收益 B = 效率收益 + 质量收益 + 产能收益
ROI = (B - C) / C
回收期 = C / 月均净收益
```

直接成本节省（缓存、路由、压缩）冲减 C，不计入 B，避免重复计算。

### 6.3 收益拆分

| 收益类别 | 算法 | 是否计入 B | 备注 |
|---|---|---|---|
| 效率收益 | 实测周期缩短或吞吐提升乘以产出量乘以单位人力成本 | 是 | 主口径 |
| 质量收益 | 返工率、缺陷率下降乘以返工成本 | 是 | 需要质量数据 |
| 产能收益 | 多交付部分乘以单位产出价值 | 条件计入 | 仅在产能被重新投入时计 |
| 直接成本节省 | 缓存、路由、压缩节省金额 | 否 | 冲减 C |

效率收益和产能收益通常是同一件事的两面，主口径选一个，另一个只做敏感性检查，两个都加就是重复计算。

### 6.4 示意算例

假设 200 个活跃开发者，月 token 成本 2 万，平台运维 1.5 万，总成本 3.5 万，时薪 150 元，每月按 4.33 周计。以下为示意，用于说明参数敏感性。

| 场景 | 每人每周节省时间 | 月收益 B | ROI |
|---|---|---|---|
| 保守 | 0.1 小时 | 约 1.3 万 | 约 -63% |
| 基准 | 0.5 小时 | 约 6.5 万 | 约 +86% |
| 乐观 | 1.0 小时 | 约 13.0 万 | 约 +271% |

同样的成本和数据，仅节省时间参数不同，结论就从亏损变成高回报。所以 ROI 必须给区间和参数，不能只给单点。

### 6.5 参数与版本管理

| 参数 | 说明 | 维护方 |
|---|---|---|
| 岗位时薪 | 按角色分档 | 财务 |
| 产能转化率 | 节省时间被重新投入生产的比例 | 业务负责人 |
| 返工成本 | 每次返工的平均人力成本 | 团队负责人 |
| GPU 利用率 | 本地算力分摊的分母假设 | 运维 |
| 基线窗口 | 每个场景的反事实基线 | 数据负责人 |
| 评分权重 | 五维权重 | 管理层 |

所有参数带版本号和来源，写入 ROI 快照表，历史快照冻结不可改。

### 7.3 聚合调度

夜间定时任务按顺序执行：session 汇总，维度日聚合，价值指标合并，分数计算，ROI 快照。按日幂等，支持任意日期补算。分数表写入参数和权重版本，保证同一日期重算结果一致。

### 7.4 身份映射

网关 user_id 对 user 表邮箱，再对 Git 提交邮箱。不一致的建映射表人工维护。映射质量直接决定人均与每 PR 指标是否可信，需要定期对账。

### 8.2 看板结构

| 页面 | 内容 | 面向 |
|---|---|---|
| 我的使用 | 额度、用量、趋势、异常提醒 | 个人 |
| 团队效能 | 五维记分卡、成本效率、可靠性、价值 | 团队负责人 |
| ROI 驾驶舱 | 成本台账、实测增量、价值区间、参数 | 管理层 |

个人页不出现排名和团队对比，团队页默认全部聚合，成员明细需权限。ROI 驾驶舱每个数字标注实测、估算或假设。

## 10. 验收标准

| 项目 | 标准 |
|---|---|
| 成本对账 | 看板总成本与 SpendLogs 汇总误差小于 0.1% |
| 分数可复现 | 同一日期重算结果完全一致 |
| session 完整性 | session 数与请求数之和一致 |
| 查询性能 | 核心接口 P95 在 1 秒内 |
| 可下钻 | 分数可下钻到原始指标与样本量 |
| 可审计 | 参数、权重、基线版本可查询 |

## 11. 风险与开放问题

| 风险或问题 | 影响 | 应对 |
|---|---|---|
| Git 数据噪声 | 产出指标失真 | 过滤机器人，定 squash 与多人 PR 归属规则 |
| 身份映射不准 | 人均指标错位 | 映射表加定期对账 |
| 时间粒度不对齐 | 关联偏差 | 定周归属规则，统一时区 |
| 省时未转化 | ROI 高估 | 显式写转化率假设 |
| 本地 GPU 闲置 | ROI 被拉低 | 分摊按真实利用率，做敏感性 |
| 因果过度声明 | 结论不可信 | 用差分对比，给区间和置信度 |
| 口径频繁变更 | 历史不可比 | 版本化，改版重算或冻结 |

开放问题：

| 编号 | 问题 | 影响 |
|---|---|---|
| 1 | 产品线等于单个团队还是多团队归并 | 维度模型 |
| 2 | 人数与预算由谁维护、多久更新 | 人均指标 |
| 3 | Git 平台 API 可用性与邮箱映射质量 | 价值分能否落地 |
| 4 | 业务回传的关联键选 session_id 还是业务 task_id | ROI 粒度 |
| 5 | 管理层要单一 ROI 数字还是区间加假设 | 看板与汇报口径 |
| 6 | 是否有交错接入的对照团队 | 因果可信度 |
