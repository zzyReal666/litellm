# 模型接入读码路线

目标：从"能跑通一次调用"到"能独立接入一个新厂商并写测试"，用一条有确定终点的路线读代码

适用版本：本机 `learn-litellm` 分支，基线 commit `9275c80320`，LiteLLM `1.101.0`

行号提示：本文所有 `文件:行号` 都基于上面的基线。上游改动频繁，行号会漂移，定位时优先用 grep 找符号名（例如 `grep -n "class BaseConfig" litellm/llms/base_llm/chat/transformation.py`），不要死记数字

---

## 读之前先建立三个概念

**pivot 格式**：LiteLLM 内部用来互操作的形状就是 OpenAI 的 Chat Completions。所有厂商协议都翻译进这个形状，或者从这个形状翻译出去。所以"懂 OpenAI 形状"不是前置课程，而是这个项目的内部接口语言

**custom_llm_provider**：一个字符串标识，比如 `deepseek`、`bedrock`、`vertex_ai`。它同时是 model 名的前缀、config 注册表的 key、`LlmProviders` 枚举值。整条链路靠它分发

**Config 与 handler 的分工**：Config 负责"协议翻译 + 厂商差异"，handler 负责"发 HTTP、解析流式、处理重试"。绝大多数厂商不需要自己写 handler，只写 Config

## 第 0 步：先看一次真实调用的报文

看什么

- 用 Python SDK 直接调一次，注意不要经过 Proxy，先把 SDK 这条链看干净
- 启动 Proxy 时加 `--detailed_debug`，观察请求进出的报文

命令

```bash
uv run python -c "
import litellm
r = litellm.completion(model='deepseek/deepseek-chat',
                       messages=[{'role':'user','content':'hi'}])
print(r.choices[0].message.content, r.usage)
print(r._hidden_params.get('response_cost'))
"
```

要回答的问题

- 我传进去的 `messages` 和真正发给厂商的 body 差在哪
- `model` 字符串在发出前变成了什么
- `response_cost` 是谁算出来、写在哪里的

过关标准：能在 debug 日志里指出"OpenAI 形状被改成厂商形状"的那一行，并说出它属于哪个文件的哪个方法

> 这一步会打真实 API、花真实费用。没配 Key 时换成本地 ollama 或任意已配好的厂商即可，观察点不变

## 附录 B：术语对照

| 术语 | 含义 |
|---|---|
| pivot 格式 | 内部互操作形状，即 OpenAI Chat Completions |
| custom_llm_provider | 厂商标识字符串，同时是 model 前缀与注册表 key |
| Config | 一个厂商一个能力一套的翻译类，继承 `BaseConfig` |
| handler | 执行器，通用实现是 `BaseLLMHTTPHandler`，少数厂商才自己写 |
| deployment | Router 里一个具体部署，`model_name` 是对外名，`litellm_params.model` 是真实 `provider/model` |
| mode | 成本表里的能力维度，如 chat / responses / embedding，决定走哪条桥 |

## 附录 C：接入新厂商的最小改动清单

1. `model_prices_and_context_window.json` 加模型条目（价格、上下文窗口、`supports_*`、`litellm_provider`）
2. `litellm/types/utils.py` 的 `LlmProviders` 加枚举值
3. 建 `litellm/llms/<provider>/chat/transformation.py`，继承 `OpenAIGPTConfig` 或 `BaseConfig`，只写差异
4. `litellm/utils.py:7999` 的 `ProviderConfigManager._build_provider_config_map` 加一行
5. `litellm/main.py` 分发链加一个 `_complete_<provider>` 分支
6. 按需：`cost_calculator.py`（缓存价、阶梯价），`messages/transformation.py`（厂商也有 Anthropic 兼容入口时），`chat/handler.py`（流式协议非标准时）

如果厂商是纯 OpenAI 兼容且无参数差异，第 3 到 5 步可以全部省掉，只往 `litellm/llms/openai_like/providers.json` 加一段 JSON

不要跟着抄的坏例子：`litellm/utils.py:4616` 里还有一份 `get_optional_params` 的 DeepSeek 专用分支，与 `ProviderConfigManager` 那条路并存做同一件事，属于历史双轨，新厂商不要再加

## 附录 D：已经踩到的坑（先记下来）

- DeepSeek 一方条目在成本表里整体落后于厂商现状：表里最新的 V4 条目是 2026-06 加的，而厂商文档现在只列 `deepseek-flash`（旧名 `deepseek-v4-flash` 与 `deepseek-v4-flash-vision-exp` 仍被接受，但请求由 V4.1-Flash 服务）和 `deepseek-v4-pro`（官方公告 2026-09-14 起把请求全部路由到 V4.1 Flash），表里没有 `deepseek-flash` 这个条目
- 表里的单一价格表达不了厂商的峰值/非峰值两档价，输出侧差异尤其明显
- 表里存在"有 key 但厂商已下线"的条目，例如 `deepseek/deepseek-coder`、`deepseek/deepseek-r1`
- 一方历史 DeepSeek 条目普遍没有 `deprecation_date`，反而第三方托管的同名模型有，所以 `/v1/model/deprecations` 帮不到使用一方 id 的人
